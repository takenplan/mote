# Recording outcome and runtime regression scenarios

Generated fixtures use formal recording owner APIs, FileStore intake, actual engine/operation projections, restart, and the real Python HTTP worker with generated dependency stubs. No personal audio or screenshots enter fixtures.

| Journey | Required evidence |
| --- | --- |
| Successful empty export | Header-only/blank/empty timestamp exports archive raw data and audio, report no text, create no Memory/full-text, survive restart, and later accept text without another audio download. |
| Unsupported nonempty export | Adapter retains original data and returns a specific format fault. Missing matching artifact is contract failure; explicit 2091003 is transient; DingTalk incomplete versus complete-empty remain distinct. |
| Old failures and long history | Failure preview includes old faults/title; authenticated bounded cursor pages enumerate all current steps without duplicates. |
| Archive and summary omissions | New membership is optional before admission; old blocked membership is repaired across restart with zero model replay. List/detail/filter/counts agree; optional configuration faults remain optional issues, not normal skips. |
| Program recovery | Provider backoff shows retry-wait, terminal failure needs action, expired child recovery terminates its parent, and canonical file details agree despite a stale program mirror. |
| Ambiguous versus known reject | A bare 503 retains the issued-call guard. A structured local not-started rejection permits ordinary retry. Restart and late responses preserve token/fence protection. |
| Native readiness | Python-only installation is separate from a system-command preflight; `ffmpeg` gaps appear in health. Missing dependencies do not hide control endpoints. Authentication, worker caps, deadlines, timeout cleanup, subsequent requests and parent shutdown retain coverage. |
| Owner boundaries | Confirmation remains blocked internally but shows the required confirmation. Explicit versus authority cancellation preserves reason. Actual operation kinds have labels and filters. No ZIP confirmation or scope/privacy changes occur. |

Android projections also cover scheduled omissions, confirmation and unknown outcomes; capture-only legacy recording responses remain compatible while updated clients explicitly request empty export receipts. Physical Android validation is separate.

Run `npm run check:affected` for changed components and consumers. Browser validation uses the isolated generated settings/operations fixture. Live local audio validation uses generated macOS TTS and the managed Native startup/shutdown path with the fixed installed models, and is reported separately from fixture assertions. Actual personal recording rechecks and historical reprocessing are owner-authorized operations, not automated tests; record their outcomes privately, including unavailable inputs, failures, and unreviewed semantic results.
