# Agent 开发协作与交接

目标是缩短从需求到可合并版本的时间，同时保留真实用户旅程、数据安全和消费者验证。稳定规则见 [AGENTS.md](../AGENTS.md)，命令与回执规则见[开发指南](development.md#validation-stages)。本文件用于当前派单；历史方案和聊天中的“一更新 PR 就完整检查”等措辞不再作为通用要求，历史执行证据保留原样。

## 按任务规模组织工作

普通模块需求或局部修复，由同一负责人完成理解、实现、定向验证、候选检查与 CI 返修。在任务记录或 PR 正文写清目标、验收与证据即可，无需额外协调者、独立任务数据库或每步一份文档。涉及架构、授权、隔离、生命周期、数据安全或公共契约的变化，沿用[技术方案审查分级](development.md#technical-plan-review)。

跨模块需求采用以下分工；角色可以按任务合并，不要求每个角色都常驻一个 Agent：

| 责任 | 负责人 | 交付内容 |
| --- | --- | --- |
| 目标与整体完成条件 | 协调者 | 用户旅程、范围、关键约束、模块依赖、集成负责人；需要用户决定的产品/架构选项 |
| 模块行为与局部验收 | 模块负责人 | 当前与预期行为、正常/失败/恢复场景、直接消费者、具体测试与缺口 |
| 相邻接口 | 相关模块共同确认，一个接口 owner 记录 | 输入输出样例、身份/授权、状态与错误、版本、重试和幂等语义；只列与本次变化相关的部分 |
| 共享文件与滚动集成 | 指定文件 owner 和集成负责人 | 唯一写入归属、合入顺序、精确提交组合、最小真实链路与最终验证计划 |
| 独立评估 | 适用审查规则要求的 reviewer | 检查验收是否覆盖目标、关键边界与实际证据，报告遗漏；不重复实现同一模块 |

协调者先定义整体目标，执行者补充模块验收并与邻接模块核对，随后按风险完成适用的独立方案审查。技术细节由负责人推进；影响用户行为或公共架构的取舍按已有决策边界处理。开发过程中发现新的验收缺口时更新现有记录，不另起一套重复清单。

## 尽早接通一条真实跨模块路径

以“Android 同步文件，中央处理，Web 展示结果”为例，最早的联调目标可以是：

| 模块 | 最初完成的一小段 | 联调时检查 |
| --- | --- | --- |
| Android | 选择一个生成的 TXT，通过真实登录凭据上传 | 请求字段、账号身份、上传结果与重试标识 |
| Server | 实际验证身份、接收文件、写入隔离存储，提供查询 | 所有者归属、返回状态、同账号可读；涉及隔离时加入另一账号对照 |
| Web | 通过真实 API 查询并显示该账号文件记录 | 返回字段、可见状态、错误与权限处理 |

三方确认接口后同时开工；API 未就绪时可用相同样例推进 UI 或客户端局部开发，真实路径可用就立即接通并记录组合版本。这条路径只证明上传、存储与展示的接线；解析、Memory、自动同步、断网恢复等后续能力继续并行开发，并逐步接入、补验。

最小路径围绕本次最容易发生错误假设的边界选择。如果需求核心是 Memory 更新，就将“原件修改 → 实际触发处理 → 新版本被查询”纳入早期路径。外部模型可以使用授权范围内的生成 fixture，并在证据中标记；所声称已验证的内部 API、存储、调度和生命周期应实际运行。

接通小路径后继续滚动集成，不等待所有模块完整交付才首次联调。需要重型完整验证时，先合入已知修改、让高风险状态的定向检查通过，再冻结候选；实现工作可在独立工作树继续，避免修改被测候选的输入。

## 交付阶段与任务事实

使用[验证阶段](development.md#validation-stages)中的统一含义：

| 阶段 | 最小证据 | 下一责任 |
| --- | --- | --- |
| `implementation-complete` | 范围内行为、提交或工作树差异、定向命令与结果、未验项 | 集成负责人接入；模块负责人继续处理相关修复 |
| `integration-verified` | 指定真实链路、组合版本、输入、状态与结果 | 继续补全其余旅程或形成最终候选 |
| `merge-ready` | 最终候选的 affected 计划、所需旅程、适用 CI 和未决项处理结果 | 按仓库合并规则交付；只有具备合并授权时执行合并 |

“已交付到 main/发布版”额外检查提交实际存在于所称目标。直接面向 main 的独立子 PR 走自己的最终检查；功能分支内的阶段性成果以明确阶段交接。模块负责人无需为证明自己的阶段工作完成而先跑整个组合的完整检查。

任务进度与验证阶段分别记录：

- 已派发：保存任务与负责人；实际会话/进程启动并确认后才记为运行中。
- 运行中：使用会话、进程或工具返回的近期状态；旧资源占用记录需要重新核对。
- 待集成或已集成：引用实际分支、提交以及合入位置；“计划合入”单独记录。
- 验证结果：保存命令、被测输入、退出结果和证据位置。失败、取消、`UNRUN`、跳过、`REUSED` 分别标记。
- 阻塞：写明缺少的接口、环境或决策、负责人和下一动作，其他无依赖工作继续推进。

优先复用现有任务工具、Git 与检查回执。多轮复杂需求将目标、依赖、接口和关键决定保存在版本化计划中；执行状态引用实际工具结果，避免多处手工维护互相冲突的“完成”声明。凭据、个人数据、私有日志与截图保持在忽略目录，公开记录只引用必要且脱敏的证据。

## 派单模板

协调者按需要填写，不要求普通单模块需求使用完整模板：

```md
### 任务 <ID>：<模块行为>
- 目标旅程与本轮范围：
- 当前行为、预期变化、沿用的设计/约束：
- 负责人、分支/工作树、基线；共享文件 owner：
- 依赖、相邻模块、接口样例及接口记录位置：
- 模块验收：正常路径、相关失败/恢复状态、直接消费者：
- 最小真实链路中的贡献与首次联调条件：
- 本轮定向验证与所需前置；额外设备/模型验证：
- 交付阶段：implementation-complete / integration-verified / merge-ready
- 集成负责人、集成目标、最终 affected 检查与旅程归属：
- 资源：独立 profile/端口/数据库/浏览器或模拟器；清理归属：
```

派单明确阶段与证据，不附加“每次创建或更新 PR 都运行完整检查”的通用要求。相关方直接确认接口细节，协调者处理依赖和跨模块决定。共享文件指定唯一写入者；任务之间使用隔离资源，完整检查由一个 driver 负责。

## 交接与 PR 说明模板

这份记录同时可用于新上下文或 PR 正文，引用现有证据即可：

```md
### 范围与结果
- 目标行为、本轮变化及对用户的影响：
- 阶段：implementation-complete / integration-verified / merge-ready
- 分支、base/head、实际被测 checkout；已集成位置：
- 相关接口/设计决定与消费者影响：

### 验证
- 本次执行：命令、输入/环境、结果、耗时、证据位置：
- 复用证据：原始回执及驱动实际 REUSED 的任务：
- 真实链路：入口、组合版本、生成输入、关键状态与结果：
- CI：当前 revision 的 run、Job 结果；未触发/不可用的原因：
- 待验证范围、已知缺口、所需环境及负责人：

### 后续
- 下一步、依赖或需要决定的问题：
- 仍运行的任务及资源；完成的清理：
```

合并前由集成负责人补齐最终候选的证据。相同主机和工作目录中符合条件的原始回执通过驱动 `--reuse` 校验；跨工作树、跨主机的模块结果作为交接参考，不能直接充当驱动的缓存。具体输入与清理要求见[回执复用](development.md#pr-check-scope)。

## 上下文与修复责任

同一任务的实现、局部修复、联调与 CI 返修优先由原负责人在原上下文继续，不因每次工具操作或验证阶段变化就清空上下文。切换独立任务、关键假设已改变或旧尝试反复干扰判断时，先更新交接记录，再以当前代码和证据开始新上下文；上下文压缩也保留这些事实。

独立评估者使用独立上下文，先读目标、验收、变更和原始证据，自己判断覆盖与结果。需要用户直觉盲测时，先给任务目标与界面，再核对功能清单。原开发者的自评作为补充，不作为评分结论。

CI 失败由 PR 负责人读取日志、交原模块负责人处理并持续跟踪当前提交，执行细则见 [CI 反馈闭环](development.md#ci-feedback)。无需为普通返修重新让用户拆任务；新的产品决定、跨模块冲突或环境阻塞带着具体证据交协调者处理。

## 过程回顾

从已有提交、回执和 Actions 记录观察：首次真实链路接通时间、重型完整检查次数、首次 CI 通过率、候选就绪到检查通过的总耗时。区分执行、资源等待、环境准备和修复时间；只比较范围与环境可比的任务。小任务不额外建立指标表，不为采集指标重复运行测试。

后续工具改进记录在[开发指南](development.md#后续工具改进)，包括真正的快速入口、工作区内部选择、CI 分层及调度。当前工作流的自动化能力以实际脚本和配置为准。

## 设计参考

- [OpenAI：Harness engineering](https://openai.com/index/harness-engineering/)：根指令作为简短导航，复杂计划与决定放入版本化文档。
- [Ham Vocke：The Practical Test Pyramid](https://martinfowler.com/articles/practical-test-pyramid.html)：早期执行快速的边界验证，将较广、较慢的测试安排到后续阶段。
- [GitHub：工作流并发控制](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)：按 PR/分支分组处理过期执行；检查范围和依赖仍由具体工作流决定。
